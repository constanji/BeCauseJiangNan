# BeCause 检索能力说明

> **读者说明**：本文档供人类/开发理解检索架构。Agent 系统提示词见 [`instructions.md`](./instructions.md)（精简）；工具细节见 [`Agent工具参考手册.md`](./Agent工具参考手册.md)。

> 从 Agent 视角，当前检索能力分为 **两大块**：**数据库结构** 与 **知识库**。  
> 每块各有两个层次：**首选路径**（快、走缓存）与 **兜底路径**（慢、范围更广或连外部数据源）。

---

## 一、数据库结构（Schema + 值对齐）

回答两类问题：

1. **结构**：有哪些表、哪些列、什么类型、什么注释？怎么 JOIN？
2. **值对齐**：用户说的「金卡」「老客」「线上」在库里实际对应哪个字段、哪个字面量？

### 1.1 两个工具，一条降级链

```
用户问数需要表结构
        │
        ▼
┌───────────────────┐
│  light_schema     │  ← 首选：只读 pgvector 缓存，不连数据库
│  （轻量化表结构）   │
└─────────┬─────────┘
          │ success: false（未做 Light Schema 预处理）
          ▼
┌───────────────────┐
│  database_schema  │  ← 兜底：连远端数据库查 information_schema
│  （实时结构）       │     有缓存时也会先走 pgvector，与 light_schema 同源
└───────────────────┘
```

| 工具 | 角色 | 连不连库 | 典型返回 |
|------|------|----------|----------|
| **light_schema** | 首选 | ❌ 不连 | `semantic_models`（表结构）+ 可能有 `value_hints` |
| **database_schema** | 兜底 | ✅ 缓存没有时才连 | 同上格式；或实时查到的全量/单表结构 |

**Agent 规则：** 生成 SQL 前先调 `light_schema`；只有返回失败再调 `database_schema`。

---

### 1.2 Cell 单元格向量化 — 到底是什么形式？

**关键结论：Cell 不是第三个工具，也不是单独一条检索链路。**

它是挂在 **数据库结构检索** 里的一层 **「值对齐增强」**，在以下两个工具内部自动触发：

- `light_schema`（始终，只要有检索文本）
- `database_schema`（仅当 pgvector 里已有 Light Schema 缓存、且 session 里有用户问题时）

```
light_schema / database_schema（缓存路径）
        │
        ├── 结构检索 ──→ light_schema_vectors（表级，embed 整张表的 DDL）
        │
        └── 值对齐检索 ──→ cell_vectors（字段级，embed 每个 distinct 单元格值）
                              │
                              └── 输出 value_hints，例如：
                                  card.type = "gold"
                                  dim_channel.channel_name = "线上"
```

#### Cell 向量存在哪？

预处理时在「数据源预处理」页执行 **单元格向量化**，后台写入 pgvector 表 `cell_vectors`：

| 字段 | 含义 |
|------|------|
| table_name | 表名 |
| column_name | 列名 |
| cell_value | 该列的一个实际存储值（如 `gold`、`老客`） |
| embedding | 对 **cell_value 文本** 做的向量（不是列注释） |

来源：对数据库里 **文本类列**（CHAR/VARCHAR/TEXT/ENUM 等）做 `SELECT DISTINCT`，每个 distinct 值一条向量。

#### Cell 什么时候触发检索？

当工具拿到 **检索文本**（用户问题或 `query` 参数）时：

1. 对检索文本做一次 embedding
2. **并行**两件事：
   - 在 `light_schema_vectors` 里找相关**表结构**（语义 top_k）
   - 在 `cell_vectors` 里找相关**单元格值**（语义 top_k，默认 10 条，相似度 ≥ 0.5）
3. Cell 命中的值 → 写入返回体的 **`value_hints`**
4. Cell 命中涉及的表若不在结构结果里 → **自动补拉**该表的 Light Schema（最多 5 张）

#### Cell 返回什么？Agent 怎么用？

返回示例（节选）：

```json
{
  "semantic_models": [ /* 表 card、loan 的结构 */ ],
  "value_hints": "card.type = \"gold\"",
  "retrieval_info": {
    "cell_matches": [
      { "tableName": "card", "columnName": "type", "cellValue": "gold", "score": 0.82 }
    ],
    "cell_table_boost": ["card"]
  }
}
```

Agent 写 WHERE 时应用 `value_hints`，不要猜 `'金卡'`、`'Gold Card'` 等——用库里真实值 `'gold'`。

#### Cell 和 sample_values 有什么区别？

都在「数据库结构」这条线里，但层次不同：

| | sample_values | cell_vectors（Cell 向量化） |
|--|---------------|---------------------------|
| 存在哪 | Light Schema JSON 里，随表一起返回 | 独立 `cell_vectors` 表 |
| 怎么来的 | 生成 Light Schema 时采样几个值 | 预处理时对 distinct 值全量（有 rowLimit）向量化 |
| 怎么检索 | 不单独检索，随 `semantic_models` 带出 | 对用户问题做**语义检索**，命中才出现在 `value_hints` |
| 用途 | 让 LLM 看到列的大致枚举 | 把用户口语对齐到精确字面量 |

#### 没做 Cell 预处理时会怎样？

- `light_schema` / `database_schema` **结构检索照常**
- **`value_hints` 为空** — LLM 只能看 `sample_values` 或自己猜 WHERE 值
- **不需要**为此降级 `database_schema` 或换别的工具

#### 一句话总结 Cell

> **Cell = 数据库结构检索自带的「WHERE 值对齐插件」，不是独立工具；预处理写入 `cell_vectors`，调用 `light_schema` 时自动参与并输出 `value_hints`。**

### 1.3 数据库结构 — 调用示例

**常规问数（结构 + 值对齐一起拿）：**

```json
{ "command": "light-schema", "arguments": "{\"query\": \"金卡客户的贷款\", \"top_k\": 8}" }
```

**已知表名（精确拉结构，query 仍可带用户原话以触发 cell）：**

```json
{ "command": "light-schema", "arguments": "{\"query\": \"金卡\", \"tables\": [\"card\", \"loan\"]}" }
```

**Light Schema 未预处理：**

```json
{ "command": "database-schema", "arguments": "{\"format\": \"semantic\", \"table\": \"card\"}" }
```

## 二、知识库（业务知识 + Excel 指标库）

回答的问题：**指标口径、编码含义、同义词、业务规则、QA** 等——与「数据库里有哪些表」无关。

### 2.1 两个工具，一条选用链

```
需要业务/指标知识
        │
        ▼
   是否查 Excel 上传的
   指标库/映射表/字典？
        │
   是 ──┼── 否
        │         │
        ▼         ▼
 knowledge_    rag_
 discovery     retrieval
 （精细化）     （广谱兜底）
```

| 工具 | 角色 | 检索对象 | 典型场景 |
|------|------|----------|----------|
| **knowledge_discovery** | 首选（Excel 行级） | 上传的 Excel 等表格知识（`file_vectors`） | 指标编码 BMxxx、指标名称、口径、计算公式 |
| **rag_retrieval** | 广谱兜底 | MongoDB 知识库 + 可选混合文件向量 | 同义词、QA、业务知识、语义模型片段 |

**Agent 规则：**

- 查 **指标编码 / 指标库一行完整信息** → 先 `knowledge_discovery`
- 查 **通用业务含义、术语、规则** → `rag_retrieval`（生成 SQL 前建议调用）
- 两者可组合，但不替代 `light_schema`

---

### 2.2 knowledge_discovery — 精细化 Excel 行检索

**存储：** 用户在数据源上传 Excel 后，每个单元格写入 `file_vectors`（`metadata.source = excel_cell`），并保留 **整行** `full_row`。

**流程：**

```
query
  → ① ILIKE 文本包含（编码/名称精确命中优先，score=1.0）
  → ② 向量语义检索（min_score 默认 0.4）
  → ③ 按 Excel 行去重（同一行只返回一条）
  → 返回 full_row（该行所有列）
```

**示例：**

```json
{ "command": "knowledge-discovery", "arguments": "{\"query\": \"BM10012529\", \"top_k\": 5}" }
```

---

### 2.3 rag_retrieval — 全量多源知识检索

**存储：** 独立向量表（`semantic_model_vectors`、`qa_pair_vectors`、`synonym_vectors`、`business_knowledge_vectors` 等），另有文件向量混合通道。

**流程：**

```
query → embed → 多类型知识库并行向量检索
            → 默认 rerank（先取约 top_k×2 再重排）
            → 若有 entityId：约 70% 知识库 + 30% 文件向量
```

**示例：**

```json
{ "command": "rag-retrieval", "arguments": "{\"query\": \"存款余额 字段含义\", \"top_k\": 10}" }
```

**与 knowledge_discovery 的分工：**

| 用户问 | 用哪个 |
|--------|--------|
| BM10012529 是什么指标 | knowledge_discovery |
| 「存款」有哪些同义词 | rag_retrieval |
| 某业务规则怎么理解 | rag_retrieval |
| Excel 指标库某行完整定义 | knowledge_discovery |

## 三、两大块对照总表

| 维度 | 数据库结构 | 知识库 |
|------|-------------|--------|
| **解决什么** | 表/列/类型 + WHERE 字面量 | 指标口径、术语、规则 |
| **首选工具** | light_schema | knowledge_discovery（Excel 行）/ rag_retrieval（通用） |
| **兜底工具** | database_schema（连库） | rag_retrieval（范围更广） |
| **预处理** | Light Schema + 可选 Cell 向量化 | 上传 Excel + RAG 知识录入 |
| **pgvector 表** | light_schema_vectors、cell_vectors | file_vectors + 各知识类型表 |
| **Cell 的位置** | 嵌在 light_schema 内，输出 value_hints | 不涉及 |

## 四、完整问数示例（两块都用上）

**用户：** 「BM10012529 对应的对公存款，classic 卡客户有多少？」

```
① knowledge_discovery("BM10012529")
   → 指标库行：指标名称、口径、可能关联字段说明

② light_schema("classic 卡 对公存款 客户", top_k=8)
   → semantic_models：相关事实表/维度表结构
   → value_hints：card.type = "classic"   ← Cell 值对齐

③ rag_retrieval("对公存款 业务含义")
   → 补充同义词、业务规则

④ text-to-sql → sql_validation → sql_executor
```

**注意分工：**

- ① 解决「这个指标是什么」— 知识库
- ② 解决「表怎么 join、WHERE 写什么值」— 数据库结构（含 Cell）
- ③ 补充语义 — 知识库广谱

## 五、预处理检查清单

| 想要的能力 | 需要在管理端做 |
|-----------|-------------|
| light_schema 能返回表结构 | 数据源预处理 → **生成 Light Schema** |
| value_hints 值对齐 | 同上 + **单元格向量化** |
| knowledge_discovery 能查 Excel | 数据源 → **上传 Excel 指标库** |
| rag_retrieval 有业务知识 | 知识库管理 → **录入 QA/同义词/业务知识** |
