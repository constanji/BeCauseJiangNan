|------|------|-----|

SELECT index_number, standard_name, index_value,

       org_code, brchna

  AND data_dt = (SELECT MAX(data_dt) FROM kpi_result_ctcx WHERE index_number = 'BM10014140')
  AND curr_code = 'CN'
  AND org_code != '00000'

#### 策略 B — 客户/产品下钻（L2，直接用 kpi_detail）

# `cmdata.c_d_tpc_acct` 查数踩坑经验与策略总结合集

## 一、核心误判：这是一张"信用卡/分期账户表"，不是"存贷款明细表"

### 坑 1：表名带来错误预期

| 预期 | 实际 |
|------|------|
| `c_d_tpc_acct` 看起来像"TPC = Third-Party 信贷账户"，以为能查存款、贷款 | 实际是**信用卡/分期类零售账户**的快照表 |
| 以为 `acct_type_name` 会包含"对公存款""个人住房贷款"等 | 只有三个值：**人民币账户 / 融通分期账户 / 原京东标准卡账户** |
| 以为全行存款余额 683 亿应该能在这张表里复算出来 | 全表汇总 ab_bal 仅 **1.90 亿元**，差了 350+ 倍 |

> **教训**：不能凭表名猜测内容，**必须先探表**。拿到 `information_schema.columns` 后，第一步不是写业务 SQL，而是写**探表 SQL**（见下文策略一）。

## 二、如何"探表" — 6 条必跑诊断 SQL

当我意识到表可能不是预想的样子后，跑了一组"诊断 SQL"，每条都有明确目的：

```sql
-- 诊断 1：总量与日期范围（判断规模）
SELECT COUNT(*) AS total_cnt, ROUND(SUM(ab_bal)/100000000,2) AS total_bal_yi,
       MIN(data_dt) AS earliest, MAX(data_dt) AS latest
FROM cmdata.c_d_tpc_acct WHERE data_dt = '2026-05-31';

-- 诊断 2：账户类型分布（核心分类，判断表定位）
SELECT acct_type_name, COUNT(*) AS cnt, ROUND(SUM(ab_bal)/100000000,2) AS bal_yi
FROM cmdata.c_d_tpc_acct WHERE data_dt = '2026-05-31'
GROUP BY acct_type_name ORDER BY bal_yi DESC;

-- 诊断 3：机构分布（判断 org_name 粒度与值）
SELECT org_name, COUNT(*) AS cnt, ROUND(SUM(ab_bal)/100000000,2) AS bal_yi
FROM cmdata.c_d_tpc_acct WHERE data_dt = '2026-05-31'
GROUP BY org_name ORDER BY bal_yi DESC;

-- 诊断 4：币种分布
SELECT book_entry_curr_cd, COUNT(*), ROUND(SUM(ab_bal)/100000000,2) AS bal_yi
FROM cmdata.c_d_tpc_acct WHERE data_dt = '2026-05-31'
GROUP BY book_entry_curr_cd;

-- 诊断 5：五级分类分布
SELECT five_class, COUNT(*), ROUND(SUM(ab_bal)/100000000,2) AS bal_yi
FROM cmdata.c_d_tpc_acct WHERE data_dt = '2026-05-31' AND five_class IS NOT NULL
GROUP BY five_class ORDER BY bal_yi DESC;

-- 诊断 6：交叉透视（账户类型 × 五级分类）
SELECT acct_type, five_class, COUNT(*), ROUND(SUM(ab_bal)/100000000,2) AS bal_yi
FROM cmdata.c_d_tpc_acct WHERE data_dt = '2026-05-31' AND acct_type IS NOT NULL AND five_class IS NOT NULL
GROUP BY acct_type, five_class ORDER BY acct_type, five_class;
```

## 三、12 个具体"坑"与应对策略

### 坑 2：余额字段不唯一 — 13 个 bal 字段

执行 `column_name LIKE '%bal%'` 发现：
- `ab_bal`（记账余额）— 后续确认是主余额
- `curr_bal` / `prin_bal` / `cash_bal` / `term_begin_bal` / `amort_pay_bal` / `highest_acct_bal` / `repay_day_bal` 等 13 个

> **策略**：先用 `light-schema` 确认 `value_hints` / `sample_values`，再选定主力余额字段。本表用 `ab_bal`。

### 坑 3：`acct_type_name` 是信用卡语境，非存款语境

| 值 | 账户数 | 余额（亿元）| 实际含义推测 |
|----|--------|------------|-------------|
| 人民币账户 | 44,510 | 1.02 | 信用卡人民币透支账户 |
| 融通分期账户 | 1,702 | 0.86 | 分期付款类账户 |
| 原京东标准卡账户 | 3,788 | 0.02 | 京东联名卡账户 |

> **教训**：命名不一定反映银行业务分类，一定要看 `DISTINCT` 实际值。

### 坑 4：`org_name` 不是完整机构树，含"信贷分部"

`org_name` 里出现了：
- 武进**信贷分部**（不是"武进支行"）
- 苏州**安全保障分部**
- 新北**信贷分部**
- 宿城**保障分部**

这些显然不是完整的分支机构名称，是**特定业务条线的拆分**。武进支行（A0002）在这张表里几乎无法定位。

### 坑 5：`book_entry_curr_cd` 全是 `01`（人民币）

只有 1 个币种值 `'01'`，表示**没有外币数据**。

> **策略**：仍然要查，不要假设。确认后 SQL 可省略币种过滤。

### 坑 6：`five_class` 值 `'5'` 余额最高（0.95 亿），反常

| 五级分类 | 余额（亿元）| 占比 |
|---------|-----------|------|
| 5（损失类？）| 0.95 | 49.7% |
| 1（正常类）| 0.74 | 38.9% |
| 4（可疑类）| 0.08 | 4.2% |
| 2（关注类）| 0.07 | 3.7% |
| 3（次级类）| 0.06 | — |

> 这在贷款表中极为反常——通常正常类占绝对多数。但这恰好说明**这不是贷款表**。信用卡分期/消费贷类资产在五级分类口径下可能有不同映射逻辑。

### 坑 7：`acct_type = 'X'`（融通分期）+ `five_class = '5'` 占比最高

交叉表：
- `acct_type='X'`（融通分期）+ `five_class='5'` = **0.52 亿**
- `acct_type='C'`（人民币账户）+ `five_class='5'` = 0.38 亿

分期类资产核销/逾期集中，符合信用卡业务特征。

### 坑 8：`status_cd` 含 M5 / SC 等逾期状态码

| status_cd | 余额（亿元）|
|-----------|-----------|
| `' '`（空/正常）| 0.74 |
| `M5` | 0.58 |
| `SR|M5` | 0.52 |

M5 通常表示逾期 150+ 天，SC 可能为核销标记。**这进一步证实这是信用卡/消费贷逾期管理表**。

### 坑 9：武进支行（A0002）查询结果极少

武进支行在这张表里：
- `acct_type='C'`：仅 5 条，余额几乎为 0
- 武进**信贷分部**：855 条 C 类 + 40 条 X 类，合计约 0.05 亿

> **教训**：KPI 表里 `org_code='A0002'` 武进支行存款 683 亿，但明细表里完全找不到。**两张表不是同一数据口径，不要用这张明细表去验证 KPI 表。**

### 坑 10：`acct_class` 几乎全是 `'S'`

- `S`（推测为"个人/Small"类）：49,998 条，1.90 亿

这是一张**纯零售类**的表。

### 坑 11：`acct_level` 只有 H/M/L 且余额极小

- H: 530 条 / 0.02 亿
- M: 392 条 / 0.02 亿

### 坑 12：单次快照限 50,000 行

## 四、核心策略总结 — "查数三层确认法"

```
第一层：探表
  ├─ 诊断 1：总量 + 日期范围
  ├─ 诊断 2-5：核心分类字段 DISTINCT + 分布
  └─ 诊断 6：交叉透视验证

第二层：做口径映射
  ├─ KPI 表 index_code → knowledge-discovery 拿口径公式
  ├─ 口径公式 → 判断需要哪些子指标/维度
  └─ 判断能否在当前明细表中复算（对比总量级）

第三层：写业务 SQL
  ├─ 确认 data_dt 对齐
  ├─ 确认机构 org 字段对齐（KPI 的 org_code vs 明细的 org_name）
  └─ 确认余额字段选择（多 bal 字段必先确认主力字段）
```

### 最重要的决策判断：KPI 表 vs 明细表

| KPI 表（kpi_result_ctcx）| 明细表（c_d_tpc_acct）|
|--------------------------|----------------------|
| 武进支行存款 683 亿 | 武进相关全部余额 0.05 亿 |
| 全行级预聚合 | 信用卡/分期零售快照 |
| **适合：查数、排名、趋势** | **适合：信用卡逾期/分期明细下钻** |
| **不适合：拿明细验证 KPI** | **不适合：存贷款业务分析** |

> **铁律**：遇到明细表与 KPI 表总量级别不匹配（差 100 倍以上），立即判断为**不同口径/不同业务域**，不要强行对账。此时应告知用户"该明细表不覆盖存贷款业务，建议确认是否有 `c_d_tpc_loan` 或 `c_d_tpc_deposit` 等对口明细表"。
